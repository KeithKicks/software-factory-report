In plain terms

What this is, in three paragraphs

Most software projects fail in the gap between what a client means and what gets built. The Software Factory closes that gap with a structured interview. It asks one question at a time across seven areas (goals, users, connected systems, data, edge cases, security, budget and timing) and keeps asking until the plan is complete enough to build from. Only then does it start building.

Once a plan is sealed, the system writes the software, runs a set of tests against it, and if anything fails, goes back and tries again, up to three times. Every step is visible on a dashboard, and every dollar of computing cost is recorded against the client and project it belongs to.

Around that core sit fourteen business disciplines that established software companies are expected to have: security and audit trails, cost tracking, incident handling, service level commitments, change control, vendor risk, and so on. Here they are not policy documents. They are running parts of the system from the first day.

How to read this page. Green tiles and callouts describe things that exist and work today. Amber callouts describe gaps and next steps. Nothing below is a plan dressed up as a result; where something is still ahead of us, it says so.
What got built

Two systems, plus the company around them

The Forge is the interview. It scores how complete the plan is in each of the seven areas and always asks about the weakest one next. At 85 percent overall it seals the plan into a specification the build side can work from.

The Factory is the build line. Sealed plans wait in a queue. Each one moves through four stages: analysis, code writing, testing, and packaging. A failed test sends the project back for another attempt, three at most. Define, build, test, refine, all visible on screen.

What those disciplines do for a client

  • Client passwords and keys are stored encrypted, and every time one is used, that use is logged.
  • Every sensitive action leaves a permanent record of who did what, when, and for which client.
  • Every unit of AI and computing cost is attributed to a client, a project, and a build, then rolled up into margins, monthly projections, and budget alarms.
  • Problems are tracked by severity with response time clocks, and each one closes with a written review of what happened.
  • The AI models doing the work are chosen from a registry with recorded pricing and quality scores, with a backup model ready if the primary one fails.
  • Reliability targets are measured against actual uptime, not assumed.
  • Changes to the system carry an impact assessment and can be rolled out to a few clients first.
  • Lessons and reusable patterns are kept and ranked by how well they worked.
  • Bringing a client on is one step. Taking a client off removes every credential and stops every job that belongs to them.
What is real today

Real files, real tests, one gap left

The build line produces software. Each build writes a small working web service from the sealed plan, then runs that service's own automated tests. The pass and fail counts on the dashboard come from tests that actually executed. A failed run genuinely triggers the next attempt, and the quality figures are computed from those outcomes.
Two ways to write the code. With no paid AI account connected, a built-in template produces a working service that answers from the plan itself. With an AI account connected, the system asks the code-writing model for the service and its tests, and from the second attempt onward hands the model the previous failure report so it can fix what broke. The template path has been exercised end to end. The AI path exists in the code and has not yet been run with a live account.
The remaining gap is launch. A finished build is a folder of tested code with instructions. It does not yet start up at a web address on its own. That is the next phase, already scoped, and it needs no extra infrastructure. Two honest footnotes: without an AI account the template always passes its own tests, so failures only appear once real AI-written code is in play; and in that no-account mode the system still records estimated AI costs, labeled as estimates, so the money figures behave the way they will in production.

Independent review

Checked before it was reported

Before the first version of this page was published, an independent automated review examined the code from five angles: correctness of the server logic, security, separation between clients, correctness of the dashboard, and integrity of the data. Each issue it raised went to a second, separate reviewer whose job was to prove the issue wrong by tracing the actual code. Only issues that survived that challenge were treated as real.

Saying it out loud

How to explain it

Plain

A software company in a box. It interviews the client, builds the software, tests it, and runs the business disciplines around the work on its own.

For a client

We interview you until your idea is specific enough to build. Then the machine builds it, tests it against your own requirements, and shows its work, including what it cost and how reliable it is.

For an investor

The operating chassis of an AI software agency. The fourteen disciplines an acquirer checks in due diligence run as code from the first day, and the build line already produces tested software.

For a technical reader

A multi-client platform where a completeness-scored intake engine feeds a queued build pipeline that writes and tests real code, with cost attribution, model governance, audit, service level, and incident systems built into every operation.

For a skeptic

The cost ledger is real, the workflow rules are real, the client separation is tested, and the builds write and test real code. The one thing it does not do yet is launch that code at a web address. This page says so plainly.

Next

What comes next

  1. Phase C, launch. A finished build starts up at a web address and the address is recorded. Medium effort, no new infrastructure.
  2. The approval gate. Finished work currently waits for a person to mark it delivered. That is a deliberate choice, and it means the build line sits idle once everything reaches review. The decision ahead is whether to keep that human sign-off or let work move on automatically.
  3. Connect a live AI account. Everything on this page works without one. Connecting one switches the code-writing step from the built-in template to AI-written code.
