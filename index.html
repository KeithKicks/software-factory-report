What got built

Two systems, plus the company around them

The Forge interviews clients. Seven requirement categories, one question at a time, always aimed at the weakest category. At 85% completeness a session seals into a structured specification.

The Factory pulls sealed specifications through a queued build pipeline: analysis, code generation, tests, packaging. A failed test run sends the project back for another iteration, three at most. Define, build, test, refine, all visible on screen.

What is real today

Real files, real tests, one gap left

The build engine produces software. Each build writes a runnable FastAPI service to disk from the sealed specification, then runs that service's own test suite. The pass and fail counts on the dashboard are the results of tests that actually executed. A failed run triggers the next iteration for real, and quality metrics are computed from those outcomes.
Two generators share one output. With no API key, a deterministic template writes a working service whose handler answers from the specification. With a key configured, the governed router asks the code generation model for the application and its tests, and iteration two onward receives the previous failure report so the model can fix what broke. The template path is exercised end to end. The model path exists in code and has not yet been run with a real key.
The remaining gap is deployment. A passed build is a folder of tested code with a README. It does not yet launch on a port with a live URL. That is Phase C, planned and scoped, and it needs no Docker. Two honest footnotes: in mock mode builds pass deterministically, since a template passes its own tests; and the simulated per-stage token costs are still recorded in mock mode so the unit economics behave like production, labeled as simulated in the ledger.

Independent audit

Audited before it was reported

Before the first version of this page existed, a five-lens adversarial audit ran over the code: backend correctness, security, tenant isolation, frontend correctness, data integrity. Each finding went to a separate verifier instructed to refute it by tracing the real code path.

Next

What needs a decision

  1. Phase C, deployment. A passed build launches on a port and gets a URL. Medium effort, no Docker required.
  2. The idle queue. The pulse moved every project to review overnight, and delivery is a human step by design, so the live queue sits empty. Either keep that honest gate, or let the pulse also pull review projects that have no passing build yet.
  3. Live model keys. Only if you want model-written code instead of the template: set ANTHROPIC_API_KEY and FACTORY_MOCK_MODE=false. Everything else already works without them.
